# S6: BullMQ + transactional outbox vs pg-boss vs graphile-worker

Extension of `QUEUE-BENCHMARK.md` (same project, compose file, library versions and images; existing results untouched). Raw data: `results-s6-pass1/raw.jsonl`, `results-s6-pass2/raw.jsonl` (+ `environment.json`, `run.log`). Tables are generated by `scripts/report-s6.js` (also `tables-s6.md`). Pass 1 stack order: bullmq-dedicated-outbox, pg-boss, graphile-worker; pass 2 reversed. 5 runs per cell; 75 runs per pass, 0 harness errors in both.

## 1. Environment and settings

Same host, Docker VM, caps, images and versions as the main report (Redis 8.10.2, PostgreSQL 16.15, bullmq 6.3.16, pg-boss 12.38.0, graphile-worker 0.18.0, Node 24.22.0). redis-queue: `maxmemory 384mb`, `noeviction`, `appendonly yes`, `appendfsync everysec`. PostgreSQL defaults (fsync on, synchronous_commit on).

**bullmq-dedicated-outbox (new stack):**
- One PostgreSQL transaction does `INSERT INTO content_versions` and `INSERT INTO outbox (payload)`. Table `outbox(id bigserial, payload jsonb, created_at timestamptz default now(), sent_at timestamptz NULL)` **plus one column I added, `done_at timestamptz NULL`**, which the worker sets after handling a job; the reconciliation needs it. A partial index on `id WHERE sent_at IS NULL` was added.
- Relay: separate Node process. Each cycle: `BEGIN; SELECT id, payload FROM outbox WHERE sent_at IS NULL ORDER BY id LIMIT 100 FOR UPDATE SKIP LOCKED; queue.addBulk(... jobId = 'ob-<outbox id>'); UPDATE outbox SET sent_at = now() WHERE id = ANY(...); COMMIT`. **Polling: 100 ms sleep when a cycle finds nothing** (no sleep while there are rows), batch size 100 (10 in S6c).
- **jobId is `ob-<id>`, not the bare id**: BullMQ 6.3.16 rejects integer-like custom ids ("Custom Id cannot be integers").
- Queue and worker: `redis-queue`, queue `jobs`, `removeOnComplete: true` (the main benchmark's setting), worker concurrency 10, otherwise as in the main report.
- Worker marks `outbox.done_at` after counting the execution.
- Reconciliation (S6d): `SELECT id, payload FROM outbox WHERE done_at IS NULL`, then `queue.addBulk` with `jobId = 'ob-<id>'` in chunks of 1,000, regardless of `sent_at`.

**pg-boss and graphile-worker:** the existing S5 implementations (job enqueued inside the publish transaction), unchanged apart from two additive parameters in the test agent (a "kill after COMMIT" flag and a reindex-latency statistic). Same settings as the main report (pg-boss `batchSize`=N + burst, polling 2 s, no LISTEN/NOTIFY; graphile-worker defaults).

**Scenario details**
- **S6a:** per run 1,000 normal publishes (control) and 1,000 publishes where the process abandons the transaction before COMMIT (connection dropped, same injection as S5). Relay (outbox stack) runs and catches up before counting; workers are off so jobs can be counted in the queue.
- **S6b:** per run 50 separate producer processes, each does one publish and `SIGKILL`s itself immediately after COMMIT. For the outbox stack the relay then drains; counted after that. For pg-boss/graphile-worker the job is part of the committed transaction.
- **S6c (outbox stack only; pg-boss/graphile-worker have no relay step):** per run 1,000 outbox rows; 100 rounds of (relay process with batch 10 killed by `SIGKILL` right after `queue.add`, then a fresh relay re-selects the same unsent rows, re-adds and marks them). Workers (concurrency 10) either run throughout ("worker-running", the main benchmark's `removeOnComplete: true`), or are started only after all relay work ("worker-idle"), or run throughout with `removeOnComplete: {age: 3600}` ("worker-running-keep-completed", **a setting I changed to test retention; not part of the requested configuration**).
- **S6d:** 5,000 jobs waiting (no worker). Outbox stack: `docker kill -s KILL redis-queue`, AOF directory deleted from its volume, container started (empty Redis); count jobs found; run reconciliation; run a worker; count executions. pg-boss/graphile-worker: `docker kill -s KILL postgres`, restart (data directory kept), count jobs found, run a worker. **These are different failures** (total Redis data loss vs Postgres process crash), as requested.
- **S6e:** publish ms/op = 1,000 sequential publishes with no relay and no worker running. Latency = payload timestamp (taken just before COMMIT for the outbox, just before the in-transaction enqueue for pg-boss/graphile-worker) to handler start, 1,000 back-to-back publishes with the relay (outbox) and 10 workers running.

## 3. Findings (numbers only)

**Who wins each scenario**
- **S6a (crash before commit):** tie. 0 content changes without a job and 0 jobs without content for all three stacks, in 5,000 injected crashes each per pass (control publishes: 5,000 committed, 5,000 jobs, 0 orphaned).
- **S6b (crash after commit):** tie. 250 producer kills per pass per stack, 0 changes without a job. The outbox relay caught up in a median 17-19 ms (it only had to send 50 rows); for pg-boss and graphile-worker the job is committed with the change, so there is nothing to catch up.
- **S6c (relay crash between add and mark-sent):** measured for the outbox stack only. **Lost jobs: 0 in all variants.** **Duplicate executions depended on retention, not on the jobId alone:**
  - With the main benchmark's `removeOnComplete: true` and a worker running, every one of 5,000 rows executed twice (5,000 duplicates of 5,000 per pass, in both passes): the first run completed and was removed from Redis, so the re-add under the same jobId created a new job. In this test the jobId did **not** prevent duplicates.
  - With the worker idle (jobs still in Redis when re-added): 0 duplicates in 5,000 rows per pass; jobId dedup worked.
  - With completed jobs kept for 1 hour: 0 duplicates in 5,000 rows per pass. I did not test retention shorter than the gap between a relay crash and its retry, or longer gaps.
  - So the outbox gives at-least-once delivery. Whether it is effectively once depends on that retention setting or on idempotent handlers. I did not measure duplicate behaviour for pg-boss or graphile-worker under crashes of their own workers, so I make no claim about them here.
- **S6d (store loss, 5,000 jobs waiting):** the outbox stack lost 5,000 of 5,000 jobs in Redis in every run (25,000 over 5 runs per pass), then the reconciliation re-enqueued 5,000 rows in a median 215-232 ms and all were executed by about 1.0-1.05 s after reconciliation started, with 0 duplicates and 0 jobs lost afterwards. pg-boss and graphile-worker lost 0 of 5,000 across a Postgres process kill, without any extra step. Reconciliation only recovers jobs the outbox knows about and has not marked done; it does not recover anything for which no outbox row exists. Winner on not losing work without intervention: pg-boss / graphile-worker (tie). The outbox stack reaches 0 lost, but only after reconciliation.
- **S6e (cost):**
  - Publish cost: the outbox transaction (two inserts) took 0.39-0.41 ms/op, against 0.83-0.84 for pg-boss and 0.67-0.74 for graphile-worker. For reference, the main report's S5 control measured 0.57-0.58 ms/op for plain BullMQ (commit then `queue.add`), 0.79-0.84 pg-boss, 0.68-0.71 graphile-worker. The outbox figure excludes the relay's work (an extra Postgres read/lock/update per row plus a Redis add), which I did not cost separately.
  - Latency to job start: graphile-worker is lowest (p50 1 ms, p99 7-8 ms); the outbox is p95 98-103 ms, p99 104-111 ms (bounded by the 100 ms poll), but its p50 was 2 ms in pass 1 and 50 ms in pass 2 (median of runs), so I would not rely on that p50; pg-boss is p50 about 1.7 s, p99 2.0 s, which is its default 2 s polling interval with LISTEN/NOTIFY off, not a cost of the transactional approach.
  - Winner on publish cost: outbox stack. Winner on latency: graphile-worker.

**Does BullMQ + outbox match pg-boss on the publish-and-reindex guarantee?** On the failures tested here (crash before commit, crash right after commit), yes: 0 orphaned changes for both, in thousands of attempts. It does not match on everything tested: (1) after losing Redis it needs the reconciliation to get back to 0 lost jobs, while pg-boss needed nothing after a Postgres process crash (different failures, so not a like-for-like comparison of durability); (2) with `removeOnComplete: true` it delivered duplicates when the relay crashed and retried. Outside these tests, I make no claim.

## 4. What the outbox adds to the code and to operations

- **Schema:** an `outbox` table (+ `done_at`, partial index), written in every publish transaction; rows need a retention/cleanup job (not built here) or the table grows unbounded.
- **Relay process:** a separate always-on process (deployment, restart policy, one or more instances; `SKIP LOCKED` lets several run). Adds up to the polling interval to enqueue latency and constant polling load on Postgres (here 10 queries/s when idle).
- **Idempotency:** jobId convention (`ob-<id>`, not an integer) and a policy for completed-job retention, since dedup only works while the job still exists in Redis; handlers should be safe to run twice.
- **Reconciliation:** a documented, tested procedure (re-enqueue rows with `done_at IS NULL`) plus the worker writing `done_at` back to Postgres on every job (one extra Postgres write per job). It needs to run after a Redis loss, and its speed here (about 1 s for 5,000) says nothing about much larger backlogs.
- **Monitoring that the design needs (not built here):** age of the oldest row with `sent_at IS NULL` (relay stuck), count of rows with `done_at IS NULL` older than a threshold (lost or stuck jobs), relay errors/restarts, outbox table size.
- **Data stored twice:** the payload lives in Postgres and Redis.

## 5. Limits

- Single laptop, one Docker VM; load generator, relay, workers and producers share the 3-CPU runner.
- Crashes are process kills and dropped connections, not power loss, disk loss, or network partitions. The Redis "wipe" is deleting the AOF directory after a process kill; the Postgres case keeps its data directory.
- Synthetic jobs (no-op reindex), 1,000-5,000 jobs per cell, 5 runs per cell, 2 passes; no confidence intervals.
- S6c duplicate counts reflect one specific timing (relay restart about a second after the crash, jobs complete in milliseconds); other timings or slower jobs would change them. The keep-completed variant uses a setting different from the main benchmark.
- S6e latency uses 1,000 back-to-back publishes (about 0.4-0.8 s total), so the outbox p50 depends on where the burst falls relative to the 100 ms poll; the relay cost is not isolated.
- pg-boss latency reflects polling with LISTEN/NOTIFY off (library default), not its best case.
- Only BullMQ on redis-queue was tested with the outbox; the shared-Redis stack was not.
