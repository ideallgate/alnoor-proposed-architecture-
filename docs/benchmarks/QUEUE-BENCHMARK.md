# Noor job-queue benchmark: BullMQ vs pg-boss vs graphile-worker

Everything ran inside Docker on one MacBook (Docker Desktop VM: 8 CPUs, 7.75 GiB). Raw data: `results-pass1/raw.jsonl`, `results-pass2/raw.jsonl` (one JSON line per run, every error included), `environment.json` per pass, `run.log`. Tables below are generated by `scripts/report.js` (also saved as `tables.md`). Pass 1 ran stacks in the order bullmq-dedicated, bullmq-shared, pg-boss, graphile-worker; pass 2 in the reverse order. 5 runs per cell, medians reported; error counts are totals across the 5 runs.

## 2. Settings used per stack

All stacks: queue name `jobs`, one queue for all job kinds, jobs enqueued in batches of 1,000 (`addBulk` / `insert` / `addJobs`), no priorities, no rate limits, no retries injected, no handler errors thrown. Worker concurrency N in {10, 50} is the number of jobs in flight. Worker code runs in a separate Node process from the producer.

| setting | bullmq-dedicated / bullmq-shared | pg-boss | graphile-worker |
|---|---|---|---|
| Concurrency N | `Worker({concurrency: N})` | `work('jobs', {batchSize: N, localConcurrency: 1, burstWhenBatchFull: true})`, handler runs the batch with `Promise.all` | `run({concurrency: N})` |
| Connection pool | ioredis connections (library managed), `maxRetriesPerRequest: null` on workers | pool `max` = 3 for worker (see note), producer pool default 10 | worker pool `max` = N+2, producer pool 10 |
| Polling / wake | blocking Redis commands + delayed-job markers (library) | `pollingIntervalSeconds` default 2 s; LISTEN/NOTIFY **not** enabled (opt-in, default off) | LISTEN/NOTIFY for new jobs (built in); `pollInterval` default 2000 ms for delayed jobs |
| Completed jobs | `removeOnComplete: true` (docs recommend auto-removal; deleting matches graphile's default); failed jobs kept | pg-boss defaults (completed jobs retained, archived by maintenance) | default (job row deleted on success) |
| Retries | library defaults (1 attempt) | library defaults (retryLimit default of the version) | library default `maxAttempts` 25 |
| Delayed jobs | `delay` ms computed at add time | `startAfter: Date` | `runAt: Date` |
| Maintenance | defaults | defaults (maintenance/supervise/schedule on, in every process that calls `start()`) | defaults |
| Schema reset between runs | `queue.obliterate({force: true})` | `DROP SCHEMA pgboss CASCADE` then `start()` | `DROP SCHEMA graphile_worker CASCADE` then migrate |

**pg-boss concurrency, a deviation from "pure defaults":** the first attempt used `localConcurrency: N` with the default `batchSize: 1`. In a probe, 10 workers completed 10 jobs per 2-second polling interval (about 5 jobs/s), because each worker polls once per interval. That is not a fair representation of the library, so concurrency N is expressed with `batchSize: N` and `burstWhenBatchFull: true` (the throughput options described in its type docs). A side effect: a batch finishes when its slowest job finishes, and pg-boss uses 3 pooled connections for fetch/complete. This is the one place where I chose a non-default; I did not look for further tuning for any stack.

Other harness details. Job payload `{kind, i, t}` (S4 adds 1 KB padding). Pickup latency = handler start minus the producer timestamp taken just before each 1,000-job batch was submitted. Lateness = handler start minus the scheduled due time. Duplicates are counted by job id inside the worker process (executions minus distinct); lost = accepted-by-enqueue minus distinct executed; "failed" = library failed/error events plus failed rows left in the store plus handler errors. Nothing is retried by the harness; enqueue errors are counted, not hidden.

## 3. Scenario definitions as implemented

- **S1** Worker started first, then 50,000 `noop` jobs enqueued while it consumes. "enqueue/s" is therefore measured with the consumer running. "total ms" = first enqueue to last handler end. Pickup latency here includes time spent waiting in the backlog (producer is faster than the consumers), so it mostly mirrors total time, not an idle-system latency.
- **S2** 10,000 `delayed` jobs (no-op) are enqueued first, all due at the same whole second 10 s ahead; then 5,000 `audio` jobs (async 200 ms wait). Floors: 5,000 x 200 ms / 10 = 100 s at N=10, 20 s at N=50. All jobs are in one FIFO-style queue with no priority lane.
- **S3** Express `GET /hadith/rand` (same 3-table join and seed data as the Noor kit, 20,000 hadith x 3 riwayat; `rand` picks an id server-side, 80% from the first 2,000 ids, because `ab` can only request one URL). Redis cache-aside, TTL 300 s, cold cache each run, PG pool 10. `ab -k -c 100 -t 60`. Queue load: one S2 cycle at worker concurrency 10 started 2 s after `ab`; it covered the whole 60 s window in every run. Cache goes to redis-shared for bullmq-shared and baseline-shared, redis-cache otherwise.
- **S4a/b** redis-shared at 256 MB: 20,000 waiting BullMQ jobs (1 KB payload, about 34 MB), then 50,000 cache writes of 8 KB (about 410 MB). Then a worker (N=50) tries to drain, stopping if it makes no progress for 20 s. S4b also tries 1,000 extra enqueues.
- **S4c** 20,000 jobs enqueued, `docker kill -s KILL` immediately after the last enqueue is acknowledged, container restarted, remaining jobs counted, then executed by a worker.
- **S5** "Publish a content version" = INSERT into `content_versions` + enqueue a reindex job. 1,000 publishes per run with an injected crash at the critical point, plus 1,000 control publishes with no crash, plus 20 real `SIGKILL`s of the process per run. BullMQ: COMMIT, then crash, then (never reached) `queue.add`. pg-boss: `boss.send(..., {db})` using the same transaction's client; graphile-worker: `SELECT graphile_worker.add_job(...)` on the same client; for both the crash is injected after the enqueue statement and before COMMIT (the connection is dropped, so the server rolls back). The injected crash is an exception that abandons the operation (not a process kill); the SIGKILL variant is a real process kill at the same points.

Notes on the tables:
- **S1 / S2 CPU%** is `docker stats` (100% = one core). PostgreSQL (cap 1 core) averaged 52-94% in S1 for pg-boss and graphile-worker, so those two were close to Postgres-CPU-bound on this setup; Redis averaged about 30% (cap 0.5 core, so about 60% of its cap) for BullMQ. Peak Redis `used_memory` and per-container memory are in `raw.jsonl` under `resources`.
- **graphile-worker S1 got slower at N=50 than N=10** (1.7k vs 2.5k jobs/s median, both passes). I did not investigate the cause; Postgres was at ~91-94% of its CPU cap.
- **S2 lateness is dominated by queue order, not by timer precision.** The burst is due 10 s in, while 5,000 audio jobs are still running. BullMQ moves due delayed jobs to the end of the wait list and graphile-worker orders by `run_at`, so both put the burst behind the remaining audio backlog (about 94 s late at N=10). pg-boss orders by creation time, and I created the delayed jobs *before* the audio jobs, so its burst jumped ahead (2-3 s late, mostly its 2 s polling interval). With the enqueue order reversed, or with a separate priority queue for notifications, these lateness numbers would change. Do not read the lateness column as "pg-boss is better at delayed jobs".
- **S3** requests/s is limited by the single-process Express app and `ab` sharing the runner's CPUs (about 130% of 300% used), and cache hit rate was about 98%, so PostgreSQL saw few queries.
- **S4a (allkeys-lru):** 50,000 cache writes all succeeded and Redis evicted about 44,000 keys, including the whole BullMQ wait list (length 0 afterwards). A few hundred orphaned job hashes remained (339-676) that no queue structure points to. 20,000 of 20,000 jobs were lost in all 10 runs; no job was left partially intact, so "corrupted" jobs were 0 and "lost" jobs were all of them.
- **S4b (noeviction):** 22.5k of 50k cache writes failed with `OOM command not allowed`, and all 1,000 extra queue enqueues failed too (the queue shares the full instance). The 20,000 jobs stayed intact in Redis (wait list 20,000, all with hashes). But in 7 of 10 runs the worker made zero progress for 20 s (about 185,000 library error events each), because moving a job to active also needs memory; in 3 of 10 runs it drained all 20,000. The "jobs lost" column there counts jobs not executed within the test window; none were deleted.
- **S4c:** only redis-shared with no persistence lost jobs. The kill is a process kill (the OS page cache survives), so this does **not** test power loss or a host crash; Redis AOF `everysec` can lose up to about a second of writes in that case, which this test cannot show.
- **S5:** the BullMQ rows are the expected result of committing before enqueueing; "content committed" for pg-boss and graphile-worker is 0 because the crash rolled back the whole transaction (content change and job together). Control runs with no crash show 0 orphans for all stacks, so the check itself works.

## 5. Findings (numbers only)

**Who wins each scenario**
- **S1 raw throughput:** BullMQ wins. bullmq-shared 8.9-9.4k jobs/s and bullmq-dedicated 7.1-7.5k jobs/s, against pg-boss 1.3k (N=10) / 4.3k (N=50) and graphile-worker 2.5k (N=10) / 1.7k (N=50). Total time for 50,000 jobs: 5-7 s for BullMQ, 11-40 s for pg-boss, 20-30 s for graphile-worker. Both passes agree. bullmq-shared was faster than bullmq-dedicated in all four cells of both passes; the dedicated Redis has AOF on and the shared one does not, which fits that difference, but I did not test it in isolation.
- **S1 enqueue rate:** pg-boss wins (about 49-51k jobs/s with batch `insert`) over graphile-worker (11-26k) and BullMQ (13-19k). Caveat: producer and consumer ran together.
- **S2 completion time:** BullMQ is fastest by a small margin (about 105 s vs 106 s graphile-worker and 110-111 s pg-boss at N=10; 22.2-22.5 s vs 24.5-26.0 s at N=50). All are close to the 100 s / 20 s theoretical floors, so the differences are small.
- **S2 delayed-job lateness:** pg-boss has the lowest numbers (p95 about 1.1-3.8 s), but this is the queue-order effect described above; it is not evidence of better timing in general.
- **S3 API interference:** no consistent effect. In pass 1 every cell is within about 2% of baseline on req/s (18.7-19.3k vs 18.8-19.0k) with identical p95 (8 ms). In pass 2 pg-boss was about 6% lower in req/s (17.0k vs 18.2k) with p95 10 ms vs 9 ms; graphile-worker was about 1.6% lower, and BullMQ shared/dedicated were not lower. With 5 runs per cell and a loaded laptop, I cannot call the pg-boss pass-2 gap a real effect or noise; it did not appear in pass 1. Shared Redis for queue + cache showed no measurable API cost at this load, with the queue only briefly busy and the cache small.
- **S4 eviction / durability:** BullMQ on a shared Redis with `allkeys-lru` lost all 20,000 jobs under cache pressure; with `noeviction` it lost none but failed 55% of cache writes and all new enqueues, and the worker often could not make progress. A BullMQ Redis with no persistence lost 20,000 of 20,000 on a hard kill. BullMQ with AOF everysec, pg-boss and graphile-worker lost 0 of 20,000 on a process hard-kill in all 5 runs of both passes.
- **S5 transactional enqueue:** pg-boss and graphile-worker: 0 content changes without a job, in 5,000 injected crashes and 100 real SIGKILLs. BullMQ (commit then enqueue): every injected crash left a committed change with no job (5,000 of 5,000, and 100 of 100 SIGKILLs). Publish cost with no crash was 0.5-0.6 ms (BullMQ) vs 0.7-0.8 ms (Postgres stacks) per operation including the DB write.
- **Errors:** across all S1 and S2 runs, lost jobs = 0, duplicate executions = 0, failed jobs = 0, enqueue failures = 0, harness errors = 0 for every stack.

**What the numbers do not say**
- Nothing here shows which stack suits Noor's production load, which is far smaller than 10k jobs/s. Throughput differences matter only if the real workload gets near them.
- BullMQ's S5 result describes the plain "commit then enqueue" pattern; an outbox table or re-enqueue-on-startup would change it, and I did not test those.

## 6. Limits

- Single laptop; Docker VM with 8 CPUs and the load generator, API, workers and producers sharing the 3-CPU runner container. CPU contention there affects every stack, and S3 cannot separate store interference from runner CPU contention.
- Small cell counts (5 runs, 2 passes). I report medians and min/max only where noted; I did not compute confidence intervals.
- Synthetic jobs (no-ops and 200 ms waits), one queue, no priorities, 1 KB payloads in S4 only.
- pg-boss was run with a non-default concurrency setup (explained in section 2) and without LISTEN/NOTIFY; other reasonable settings for any stack (BullMQ with removeOnComplete off, Postgres tuning, Redis `io-threads`, pg-boss `notify`) were not explored and could change results.
- S1 latency includes backlog wait; S2 lateness depends on enqueue order and queue policy (above).
- S4c and S5 use process kills and simulated crashes, not power loss, disk failure or network partitions. Postgres durability was the default (fsync on, synchronous_commit on).
- Versions are the latest at run time (2026-10-18) and several are newer major versions (bullmq 6, pg-boss 12, ioredis 6); results may not carry over to older releases.
- The existing Noor kit was used only for the hadith seed and query; its other scenarios were not run.
